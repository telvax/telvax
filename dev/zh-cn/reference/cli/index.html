This is the documentation of the development version (the main branch). It can describe things that are not released yet.

Command line

此内容尚不支持你的语言。

telvax is one program with several commands: telvax <command> [options]. telvax --version prints the version and telvax --help prints the list below. telvax doctor says what the build you have can do. The package manager, tvpm, is at the end.

Synopsis

Section titled “Synopsis”

This block is the output of telvax --help, and a test checks that it still is.

Exit status

Section titled “Exit status”
Status Meaning
0 The command did what it was asked.
1 It failed: a program with errors, a failing test, a file that needs formatting, a missing file. The reason is printed after error:.
2 It was called wrongly: an unknown command (with a suggestion when one is close) or options that do not fit.

Options several commands share

Section titled “Options several commands share”

--allow list : The permissions the program has: fs.read, fs.write, fs (both), env, net, all or none, separated by commas (--allow fs.read,net). A function that needs one that was not given stops with an error. Without --allow everything is allowed. Taken by run, test, profile, repl and serve. (lint has its own --allow rule, see below.)

--quantize int8 | int8-channel | int4-channel | none : Runs f32 matrix products with integer arithmetic. See the section Quantization of the tour. Taken by run, serve and build.

--device cpu | gpu : Where tensor operations run; gpu needs a build with the gpu feature and a GPU (telvax doctor says if the build has it). Taken by run and serve.

--workers host:port,host:port : Sends the calls of std.dist.map to machines that run telvax worker. The environment variable TELVAX_WORKERS is the default. Taken by run and serve.

Commands

Section titled “Commands”

telvax check

Section titled “telvax check”

Parses and type-checks the files named, or, with none, the package in the current directory (the one with a telvax.toml). Prints each error with its place, and fails if there is any. --json prints the diagnostics as JSON, one object each with file, line, column, end_line, end_column, severity, message and notes, for editors and scripts.

telvax lint

Section titled “telvax lint”

Checks a file, then reports code that is not used: variables, functions, cases that can never be reached. --list-rules prints every rule with what it finds. The level of a rule (allow, warn, deny) comes from the [lint] table of telvax.toml and then from the flags --allow rule, --warn rule and --deny rule. --deny-warnings makes a warning fail the command.

telvax fmt

Section titled “telvax fmt”

Rewrites files in the one format Telvax has, and prints formatted <file> for each one it changed. A folder means every .tvx file under it; no path means the current directory; - reads the source from the standard input and writes the result to the standard output. --check changes nothing and fails if a file would change, which is what a CI job wants. --diff shows what would change.

telvax schema

Section titled “telvax schema”

Reads a .csv, .parquet or .arrow file and prints the type for its columns, to paste above let t: Table[Sales] = read_csv("sales.csv"). A CSV is read in full: its header gives the names and its values the types (Int, Float, Bool, Date, Timestamp, else Text), and a column with an empty value is written T?. For Parquet and Arrow the file’s own schema is used, including which columns may be empty. The type is named after the file (sales_2024.csv gives Sales2024); --name Row picks another name. A column whose name is not a valid field name (unit price) is reported, not renamed.

telvax doc

Section titled “telvax doc”

Writes a Markdown reference of the functions, types, enums and traits in the files named (a folder means every .tvx file under it), with the # comment lines written directly above each one. --public leaves out the names that start with _. -o out.md writes a file instead of the standard output.

telvax test

Section titled “telvax test”

Runs the functions named test_... in a file; a test passes when it returns and fails when it stops with an error (assert, assert_eq, fail, any runtime error). A folder runs every test_*.tvx and *_test.tvx file under it. A second word, name, runs only the tests whose name contains it. It prints N passed, M failed and fails if any test did. --coverage also reports which lines of the program the tests ran; --fail-under N (0 to 100) turns that into a gate: the command fails if fewer than N percent of the lines ran. The functions of std.test, such as mock, are in the library reference.

telvax run

Section titled “telvax run”

Calls a function of a program: telvax run app.tvx main, or just telvax run app.tvx to call main. The words after the function name are its arguments, in order. A Text parameter takes the word as it is; any other type takes JSON (3, true, [1, 2], {"a": 1}). The value the function returns is printed, unless it returns nothing.

telvax profile

Section titled “telvax profile”

Runs a function like run and reports where the time and the memory went: per function, per line and per std operation. --top N limits the report to the N statements that took the longest. --json file, --collapsed file (for flame graph tools) and --speedscope file also write the report in those formats.

telvax doctor

Section titled “telvax doctor”

Prints the version, the syntax editions it reads, what this build can do (tables, live services, GPU, native backend) and the environment variables that matter (TELVAX_LIVE, OLLAMA_HOST, OPENAI_API_KEY, TELVAX_WORKERS, TELVAX_CLUSTER_TOKEN). A key or a token is shown as set or not set, never its value. Put the output in a bug report.

telvax repl

Section titled “telvax repl”

Starts an interactive session: type definitions, variables and expressions, and see the result. Files named on the command line are loaded first. The same session is in the playground. In the session, :help lists its commands.

telvax dap

Section titled “telvax dap”

The debug adapter (breakpoints, stepping, variables), speaking the Debug Adapter Protocol over the standard input and output. Editors start it; the VS Code extension does. You do not run it by hand.

telvax lsp

Section titled “telvax lsp”

The language server, speaking the Language Server Protocol over the standard input and output. Editors start it; the VS Code extension does. You do not run it by hand.

telvax worker

Section titled “telvax worker”

Runs calls for a coordinator, so that --workers can spread std.dist.map over machines. It listens on --listen host:port (default 127.0.0.1:7077) and, when --token T or the environment variable TELVAX_CLUSTER_TOKEN is set, answers only to a coordinator that has the same token.

telvax serve

Section titled “telvax serve”

Serves the @endpoint functions of a program over HTTP, with the request validated and the answer written as JSON, until it is stopped (Ctrl-C or SIGTERM). It listens on --host (default 127.0.0.1) and --port (default 8080). A program without @endpoint functions is an error. --live uses the real Ollama, OpenAI and PostgreSQL services instead of the offline stand-ins (and needs net). --seed docs.jsonl fills the vector store before the first request: one JSON object per line with the text fields collection, id and text; each text is embedded and stored.

--metrics serves GET /metrics in the Prometheus format: http_requests_total{method,path,status}, the histogram http_request_duration_seconds{method,path}, the counters the program makes with std.metrics.count(name) and the gauges it sets with std.metrics.set(name, value) (the last value wins), each under its own name (name, or name{label="value"} with labels) and its own # TYPE. A name is a counter or a gauge, not both. path is the route as written in the program, so the number of series does not grow with the ids in the URLs. --log-format json (or text) writes one line per request to the standard error: time, level, request id, method, path without the query string, status and duration. The level is info for a status under 400, warn for 4xx and error for 5xx; --log-level (or TELVAX_LOG_LEVEL) is the lowest one that is written, info by default, so --log-level warn keeps only the requests that failed. The lines of std.log follow the same format and level. With either flag every answer has an x-request-id header, the one the client sent if it is short and plain, otherwise a new one; the function can read it with req.header("x-request-id"). A program started with telvax build --serve takes the same flags, or TELVAX_METRICS=1 and TELVAX_LOG_FORMAT=json; a flag wins over the variable.

A function that fails at run time (an index out of bounds, a division by zero) answers 500 with Internal server error, in both error formats, because the interpreter’s message names the inside of the program. The message goes to the standard error with the request id, as a line error GET /path 500 request_id=...: runtime error: ... (a JSON object with --log-format json). A function that returns Err(Status.Internal(message)) keeps sending its message, because the program chose it.

Three more options go around every answer. --cors ORIGINS (*, or origins separated by commas) lets a browser page of an allowed origin read the answer: it adds access-control-allow-origin and answers a preflight OPTIONS with 204; credentials are not supported. --rate-limit N/unit (second, minute or hour) allows N requests from one client in each window, and answers 429 with retry-after after that; the client is the address of the connection, or the first address of x-forwarded-for with --trust-proxy. /healthz is never limited. --shutdown-wait N (or TELVAX_SHUTDOWN_WAIT) is the number of seconds a server that was stopped waits for its requests and background tasks (30 by default). --security-headers adds x-content-type-options: nosniff, x-frame-options: DENY, referrer-policy: no-referrer and cache-control: no-store to the answers that do not set them. The variables are TELVAX_CORS, TELVAX_RATE_LIMIT, TELVAX_SECURITY_HEADERS and TELVAX_TRUST_PROXY. The counts of the rate limit are kept in memory, per process.

These options can also be written in the program, in a serve: block of the entry file:

Each line is one of the options above (--log-format is log_format), with a fixed value: True or False, a whole number of seconds, or a text. A line can instead read a variable when the server starts, env("NAME") or env("NAME", "default"), as in cors: env("CORS_ORIGINS", "*"): the value is the text of the variable, or the default when the variable is unset or empty (with no default the line is left out), read as the flag reads it. A True or False option is on for 1 or true; the default of one is 1, true, 0 or false. telvax check refuses a default that the option would refuse; a variable that the option refuses (LOG_LEVEL=loud) stops the start with serve: LOG_LEVEL="loud" is not a value of log_level: .... Nothing is converted: RATE_LIMIT_PER_MINUTE=100 is not 100/min. telvax check reports a name that is not in the list, a value of the wrong type or one the flag would refuse, a name written twice, a second serve: block, and a block in a file that is not the entry file. A variable (TELVAX_METRICS, …) wins over the block and a flag wins over the variable. --port, --host, --live, --allow, --seed, --quantize and --device are not in the block: they depend on where the program runs. A binary from telvax build --serve keeps the block.

middleware: [names] lists functions marked @middleware, of the form fn name(req: Request, next: Next) -> Response (Request, Response and Next from std.http), outermost first. They run inside the built-in options and wrap every request, the routes and /health, /metrics, /openapi.json and /docs too. A middleware that does not call next answers by itself; one that calls it gets the Response of the rest of the chain, whose status and headers it may change (the body is passed on as it was), and next can be called once. A middleware that fails answers with 500. telvax check refuses a name that is not a function marked @middleware, a wrong signature and a name written twice, and warns about a @middleware of the entry file that the list does not mention. They run in the interpreter, which costs more than a built-in option.

on_start: [names] is the one line that is not a literal: a list of top-level functions with no parameters, each giving nothing or a Result[(), Text], which run once, in the order written, before the port is opened (so /health does not answer until they are done). They run with the permissions of the program (--live, --allow). A function that returns an Err, or fails, stops the start: the message goes to the standard error as on_start: NAME failed: MESSAGE and the exit status is 1. telvax check reports a name that is not a function, a function with parameters or another return type, and a name written twice. A function can come from another file (from db import init_db). They do not run under telvax run or telvax test.

telvax build --serve

Section titled “telvax build --serve”

Makes one executable that contains the program and the server: telvax build --serve app.tvx -o app. It copies the telvax that runs the command and appends the program, so it is as large as telvax. When started it serves the program: it listens on 0.0.0.0, on PORT if that is set, and --port and --host still win. HOST sets the address, and TELVAX_LIVE=1 turns on --live. app --healthcheck [/path] asks the server of this machine for /path (/healthz if left out; the port is --port, PORT or 8080) and exits 0 on a 2xx answer, 1 otherwise: a container has no curl for that. --dockerfile also writes a Dockerfile for it next to the program: it copies the whole directory (the other modules and the files read by std.fs.embed have to be there; a .dockerignore keeps out the rest), builds from ghcr.io/telvax/telvax (or the image in --build-arg TELVAX_IMAGE=...) and has a HEALTHCHECK that calls --healthcheck.

telvax build

Section titled “telvax build”

Compiles a program with the native backend (LLVM and MLIR), so it needs a telvax built with --features llvm; the published binaries are not, and telvax doctor says. --emit picks the output: exe (default, a program named after the file), obj (an object file), llvm-ir and mlir (printed), ptx (printed; --sm sm_80 picks the GPU generation) and stablehlo (printed). -o names the output file. -O 0 to -O 3 is the optimisation level (default 2). --emit ptx and --emit stablehlo do not need the native backend.

telvax jit

Section titled “telvax jit”

Compiles a function with the native backend and calls it at once: telvax jit app.tvx norm 3.0 4.0. Needs --features llvm.

tvpm

Section titled “tvpm”

tvpm is the package manager. It reads telvax.toml, writes telvax.lock, and runs the matching telvax command with the dependencies installed. tvpm --help prints the list of commands. tvpm finds the project in the current directory or the nearest parent that has a telvax.toml. Exit status: 0 when the command did what it was asked, 1 when it failed (the reason is printed after error:), 2 for an unknown command.

Registry

Section titled “Registry”

A registry is a directory or an http(s):// URL with the same layout: index/<name>.json has one JSON line per published version (name, vers, deps, cksum, yanked) and packages/<name>-<version>.nvpkg is a gzip-compressed tar with telvax.toml, src/**/*.tvx and the README.md and LICENSE* files if there are any. Any static file host works.

--registry <where>, before or after the command, or the environment variable TVPM_REGISTRY says which one to use. Without one, a dependency from the registry is an error that says so. Downloaded packages are unpacked in $TVPM_HOME, or ~/.tvpm, and their checksum is checked against the index.

tvpm search, publish and yank write to or read a directory registry; they do not work with a URL.

Commands

Section titled “Commands”

tvpm new <name> [--lib] : Creates the folder <name> with telvax.toml, src/main.tvx (src/lib.tvx with --lib) and a .gitignore. The name is lowercase letters, digits and single _, starting with a letter, and not std, crate, self or super.

tvpm init : Does the same in the current directory, named after it. Fails if telvax.toml is already there.

tvpm add <name>[@req] [--path DIR] : Adds a dependency to telvax.toml. name@1.2 writes that requirement; without one, tvpm looks up the newest version that is not yanked in the registry and writes ^<version>. --path DIR depends on a directory (relative to the project) whose package has that name. It does not lock or download: run tvpm install.

tvpm remove <name> : Removes a dependency from telvax.toml.

tvpm lock : Resolves the versions and writes telvax.lock. It prints each locked package.

tvpm install : Locks if telvax.lock is missing or does not match telvax.toml, then downloads the registry packages that are not installed.

tvpm update [name...] : Moves the locked versions to the newest that fit. With names, only those registry packages move, and the others stay where the lock has them unless a requirement forces them. It prints updated name 1.0.0 -> 1.1.0 for each change.

tvpm tree : Prints the dependency tree.

tvpm search <text> : Lists the packages in the directory registry whose name contains text, each with its newest version that is not yanked.

tvpm publish : Checks the package like telvax check, packs it and adds it to the directory registry. It fails if the package does not pass the check, if that version is already published (raise version first), or if it has a path dependency: a published package may depend only on registry packages.

tvpm yank <name> <version> [--undo] : Marks a published version as yanked. A new resolution skips it, and a telvax.lock that already names it still installs it. --undo marks it again as available.

tvpm check, run [fn], serve [flags], build [flags] : Lock and install if needed, then run telvax check, run, serve or build on the entry file with the rest of the words as arguments. run without a function calls main. tvpm starts the telvax next to it, or the one in TELVAX_BIN, or the one in PATH.

telvax.toml

Section titled “telvax.toml”

A version requirement is the one of Cargo: 1.2 and ^1.2 mean >=1.2.0, <2.0.0, ~1.2 means >=1.2.0, <1.3.0, =1.2.3 means that version only, and >=1, <3 combines two. Every package name resolves to one version; when two packages need different ranges of a third, tvpm picks the newest version that fits both, and fails if there is none. An edition that this telvax does not read is an error that says which ones it reads.

telvax.lock

Section titled “telvax.lock”

tvpm lock writes it; do not edit it. It has one [[package]] for the project and for each package it depends on, with name, version, source (registry or path+<dir>; none for the project itself), checksum for a registry package and dependencies, a list of names. Commit it: every machine then uses the same versions. It is out of date when telvax.toml has a dependency or a requirement that it does not cover, and install, check, run, serve and build lock again then.
